## Kronologi (append, terbaru di bawah)

### 2026-09-17 — Pemilik (pesan ke-14): "kita belum diskusi keamanan dengan sempurna … mari matangkan dulu"

Ringkasan permintaan pemilik (mendekati kata aslinya):

1. Belum pernah dibahas tuntas **mekanisme login terbaik & teraman untuk setiap peran** — kasir hanya bisa buka kasir, pelanggan hanya bagiannya, dst.; **tidak boleh ada dua rangkap fungsi**; kalau satu orang punya dua fungsi → **dua akun**.
2. Bagian staf **hanya bisa diakses di perangkat yang sudah ditentukan/didaftarkan**; admin (pusat/cabang) bisa mengelola itu.
3. Login staf harus **mudah tapi aman** — "mereka perlu kerja satset".
4. Harus diantisipasi: **perangkat kecurian/hilang lalu akunnya dipakai orang lain** (mis. tiba-tiba ada yang main aplikasi kasir).
5. "Mungkin masih banyak lagi hal terkait keamanan umum yang harus kita matangkan" — **jangan lanjut sebelum ini matang**; **merombak dokumen fondasi tidak masalah, justru bagus, karena harus tercatat**.
6. Selain keamanan: rencanakan **setiap fitur, fungsi, laman, UI, tombol** lebih matang. Pengalaman pemilik sebelumnya (dibangun dengan agent AI, walaupun 6 file fondasi sudah detail): **banyak masalah, banyak tombol kurang, fungsi katanya ada tapi tidak bisa dipakai**.
7. **Eksplisit:** ini baru ide pemilik, sangat mungkin salah → agent **tidak boleh langsung meng-iya-kan**; wajib berpikir & **meriset mendalam**, kalau ada yang tidak cocok **beri saran yang lebih baik**; gunakan **skill** yang tersedia secara maksimal.

### 2026-09-17 — Agent: riset & penyusunan usulan (belum mengubah dokumen terkunci)

**Yang diperiksa/riset (rujukan ada di naskah usulan):**

- Supabase (dokumentasi resmi): **Auth Hooks → Custom Access Token = Free** (input hook tidak membawa info perangkat); **MFA TOTP = gratis di semua proyek**; **"time-box sesi / inactivity timeout / single session per user" = Pro saja**; **leaked-password protection (HaveIBeenPwned) = Pro saja**; access token **tidak bisa dicabut** sebelum kedaluwarsa → pencabutan harus lewat pemeriksaan `session_id` di database; batas laju `/auth/v1/token` = 150 per 5 menit per IP dan **tidak ada kunci per-pengguna** bawaan → kunci percobaan harus dibuat sendiri.
- PostgREST/Supabase: header permintaan dapat dibaca di RLS (`current_setting('request.headers')`) → dipakai sebagai **bukti perangkat**, dengan catatan wajib diuji di Supabase nyata (T0-08).
- Praktik industri POS (Square "device code", passcode kasir; panduan tablet restoran): perangkat dipasangkan ke satu lokasi, pengelolaan/penulisan ulang kode perangkat, mode kiosk untuk tablet satu fungsi, rutinitas perangkat saat tutup kedai.
- UU PDP (UU 27/2022): persetujuan eksplisit, hak subjek data, **lapor kebocoran 3×24 jam**, denda administratif s.d. 2% pendapatan tahunan, tidak ada syarat lokalisasi data.
- Lingkungan kerja: **Playwright/Chromium tidak bisa dipasang di ruang kerja ini** (unduhan diblokir — sudah dicoba) → uji peramban akan ditaruh di CI; registry npm **bisa** diakses (uji komponen jsdom memungkinkan).
- Skill dibaca/dipakai: `security-review` (daftar periksa keamanan), `supabase` (daftar periksa keamanan Supabase — termasuk: jangan pakai `user_metadata` untuk otorisasi, `SECURITY DEFINER` di `public` bisa dipanggil semua peran), `supabase-postgres-best-practices`, `ui-ux-pro-max` (target sentuh/keadaan/aksesibilitas), `prd-taskmaster`, `writing-plans`, `verification-before-completion`.

**Yang dihasilkan:** `docs/teknis/USULAN_KEAMANAN_DAN_KELENGKAPAN_UI.md` — peta ancaman, desain perangkat terdaftar + sesi + PIN cepat, privasi/UU PDP, dan mekanisme kelengkapan UI (Registri Aksi + Peta Layar + pemeriksa CI + uji komponen + naskah jalan + DoD v2), dampak ke dokumen/ROADMAP, serta **6 keputusan yang diminta dari pemilik (§E)**.

**Dua keputusan yang diserahkan pemilik, ditetapkan agent (dengan alasan tertulis di `DECISIONS_LOG.md`):**

- **Satu akun = satu peran (ketat)**; `pengguna_cabang` hanya daftar cabang; izin (centang) tetap boleh berbeda per pegawai; PIN wajib unik & bukan pola lemah. Alasan: ide pemilik memang benar + satu peran membuat RLS, izin berjenjang, jejak audit, dan uji matriks izin bisa dibuktikan tanpa kombinasi tersembunyi.
- **TOTP wajib untuk `pemilik_platform`, `owner_pusat`, DAN `admin_cabang`** (bukan opsional untuk admin cabang), **dengan jalan pemulihan lebih dulu**: MFA admin cabang direset owner pusat; MFA owner pusat direset pemilik platform — semuanya tercatat + dinotifikasi. Alasan: admin cabang memang memegang akses penting (harga cabang, printer, opname, laporan cabang) sehingga pantas dilindungi; kekhawatiran "hasil kurang maksimal" ditutup dengan jalan pemulihan yang cepat dan terdokumentasi (Buku Insiden), bukan dengan menurunkan perlindungan. Kasir/pelayan/dapur tetap tanpa TOTP karena sudah dua lapis (perangkat + PIN) dan friksi hariannya paling besar.
- **Kode pemulihan MFA mandiri & pemeriksa kata sandi bocor (HIBP)** sengaja **ditunda** ke Fase 10 (T-016): HIBP adalah fitur paket Pro (menyentuh biaya) dan kode pemulihan menambah jalur rahasia baru; kompensasi sekarang = kata sandi ≥12 + larangan pola + reset berjenjang.

### PMB1-F-051 — K-2 — Batas percobaan per akun/perangkat tidak pernah aktif (galat FK melumpuhkan pencatatan)

- **Artefak:** `supabase/migrations/0087_perbaiki_search_path_kripto_dan_rpc.sql:146-156` (blok INSERT `percobaan_pin` di jalur PIN salah, kolom `perangkat_id` ber-FK ke `public.perangkat(id)`)
- **Baseline yang dilanggar:** PRD M12 (`docs/PRD.md:187`) batas percobaan per perangkat; KEAMANAN §7 (`docs/KEAMANAN.md:126`) batas 5×/15 menit per akun; penutupan temuan lama K F-03/B F-11 (`docs/uji/AUDIT_RIWAYAT.md:123`) 'ditolak seragam'; PRD M12 baris 194 (percobaan masuk berulang dibatasi dan dicatat)
- **Bukti direproduksi hari ini?** **YA** — Probe yang dieksekusi hakim F-03: `node alat/uji-sql.mjs docs/uji/pemeriksaan/PMB-1/bukti/F-03-hakim-owner-perangkat.sql` → **1 LULUS**:
  - 6 percobaan PIN salah dari 6 UUID berbeda (`p_perangkat_id` acak tak dikenal) → **6 galat basis data** `violates foreign key constraint "percobaan_pin_perangkat_id_fkey"` (karena 0087:154 menulis `p_perangkat_id` kiriman klien ke kolom ber-FK)
  - `select count(*) from public.percobaan_pin where pengguna_id = '90000000-0000-0000-0000-000000000004'` → **0 baris**
  - Akibatnya: **batas 5×/15 menit per akun (0087:118–136) tidak pernah aktif**, jejak percobaan gagal **tidak ada sama sekali** untuk penyerang yang memutar UUID
- **Analisis akar masalah (tiga cacat bersamaan):**
  1. **`p_perangkat_id` dikontrol klien** — RPC mempercayai UUID yang dikirim pemanggil untuk pencatatan kegagalan. Penyerang cukup generate UUID acak tiap request.
  2. **FK `percobaan_pin.perangkat_id` → `perangkat.id`** — kolom ini wajib merujuk perangkat yang **sudah ada** di tabel `perangkat`. Perangkat tak dikenal = INSERT gagal = rollback transaksi = **tidak ada catatan kegagalan**.
  3. **Counter akun (`v_gagal_akun`) bergantung pada `percobaan_pin`** — karena rollback, counter tidak pernah bertambah. Batas 5×/15 menit per akun **lompat di luar logika**.
- **Tingkat K tepat?** **YA, K-2** — fungsi inti (pembatasan brute-force) rusak total pada jalur ini; akuntabilitas hilang; bukan K-1 karena aksesnya sendiri (PIN benar + perangkat asing) sudah tertangkap PMB1-F-036 (K-1 TERVERIFIKASI) dan PIN tetap harus ditebak.
- **Putusan:** **TERVERIFIKASI** — status diubah `BARU` → `TERVERIFIKASI`.

### PMB1-F-052 — K-1 — Kunci rahasia perangkat (device secret key) dilewati bila `null` atau perangkat legacy

- **Artefak:** `supabase/migrations/0087_perbaiki_search_path_kripto_dan_rpc.sql:267-290` (blok verifikasi `kunci_perangkat`, baris 275–290)
- **Baseline yang dilanggar:** PRD M12:185 (perangkat terdaftar + PIN); KEAMANAN §4 (`docs/KEAMANAN.md:53-54`) rahasia hash di tabel perangkat, server hanya menyimpan SHA-256 (koreksi: bcrypt di `kredensial_perangkat.kunci_hash`); penutupan K-F-03 mewajibkan rahasia perangkat
- **Bukti direproduksi hari ini?** **YA** — Probe hakim F-03: `node alat/uji-sql.mjs docs/uji/pemeriksaan/PMB-1/bukti/H-F-03-runtime.sql` → **1 LULUS**:
  - Peran `anon` + PIN benar + UUID perangkat kasir terdaftar yang **punya hash key** → key salah ditolak (hash mismatch)
  - Key **null** (atau tidak dikirim) → **LOGIN_SUKSES** (blok `if` di baris 275 tidak dieksekusi karena `p_kunci_perangkat is not null` = false)
  - Perangkat legacy tanpa record di `kredensial_perangkat` → `exists (…)` = false → **LOGIN_SUKSES**
- **Pembeda dari temuan lain:**
  - PMB1-F-036 (K-1): owner mendaftarkan **perangkat baru** sendiri (self-provisioning). PMB1-F-052: **perangkat sudah terdaftar** (memiliki UUID dan/atau hash), tetapi kunci rahasia **tidak diverifikasi** bila null/legacy.
  - PMB1-F-039 (K-2): orakel PIN dari perangkat asing (jawaban berbeda PIN benar vs PIN salah). PMB1-F-052: **bypass rahasia perangkat** pada perangkat yang *seharusnya* memilikinya.
- **Catatan bukti:** Probe di atas = SQL lokal / kripto mock (PGlite), **bukan** uji hosted Supabase. Tingkat K-1 dipertahankan karena mekanisme kodenya **langsung membuka celah** — tidak bergantung pada konfigurasi produksi.
- **Putusan:** **TERVERIFIKASI** — status diubah `BARU` → `TERVERIFIKASI`.

### PMB1-F-052 — K-1 — `p_kunci_perangkat` null melewati pemeriksaan rahasia perangkat yang sudah terdaftar

- **Bukti direproduksi hari ini? YA.** `node alat/uji-sql.mjs docs/uji/pemeriksaan/PMB-1/bukti/H-F-03-runtime.sql` → **1 LULUS** (2026-09-29): perangkat kasir terdaftar `de000000-…-0003` yang **punya** `kunci_hash` (kontrol `exists(select 1 from public.kredensial_perangkat …)` LULUS; fixture `alat/sql/data-uji.sql:147`) → key **salah** dibalas `PERANGKAT_TIDAK_SAH`, key **null** dibalas `LOGIN_SUKSES` (PIN benar, kursi `anon`).
- **Statis hari ini:** `0087:266-281` → `if p_kunci_perangkat is not null and exists (…)` — parameter null **melewati seluruh blok** meski hash ada; tanda tangan `0087:42` `p_kunci_perangkat text default null`; `0087:321` grant execute ke `anon, authenticated, service_role`.
- **Bukti tambahan oleh hakim (baru hari ini):** `aplikasi/src/lib/auth.ts:176-181` — satu-satunya pemanggil RPC di aplikasi hanya mengirim `p_email, p_pin, p_perangkat_id, p_perangkat_nama`; **parameter key tidak pernah dikirim** oleh klien resmi → pemeriksaan rahasia perangkat terlewat pada **setiap** login aplikasi, bukan hanya pada panggilan penyerang. `grep -rn verifikasi_pin_perangkat aplikasi/src` → hanya `auth.ts:176` + registri `aksi.ts:36`.
- **Bantahan yang saya coba:** (1) "perangkat legacy tanpa key butuh jalur null" → terbantah untuk lingkup temuan: `exists(...)` + `v_kunci_hash is not null` memang menangani perangkat tanpa key-row (dan itu **demi desain**), sedangkan cacat yang diklaim adalah melewati perangkat yang **punya** key — kontrol probe membuktikan hash memang ada; (2) "mungkin ada klien lain yang mengirim key" → tidak ada di repo, malah klien resmi tidak pernah mengirim; (3) "mungkin perilaku mock kripto lokal yang berbeda" → bypass ini **struktural** (cek null di awal blok) sehingga tidak bergantung `crypt`; batas jujur tetap dicatat: bukti logika di PGlite lokal dengan kripto tiruan, **bukan** eksploitasi Supabase hosted (sudah tercatat di PMB1-A-043); (4) "prasyarat UUID+PIN menurunkan tingkat?" → UUID bukan rahasia (`0018:90` `grant select … perangkat to authenticated`, tampil di layar kelola perangkat, disimpan di klien) — tersisa hanya PIN 6 digit, padahal PRD `docs/PRD.md:185` ("hanya sah di perangkat terdaftar") dan KEAMANAN §4 (`docs/KEAMANAN.md:53-54`, `rahasia_hash` + "rahasia acak 32 byte … server hanya menyimpan SHA-256") mewajibkan rahasia perangkat; penutupan K F-03 (`AUDIT_RIWAYAT.md:123`) juga berdiri di atas "kunci … di `kredensial_perangkat`".
- **Perbedaan bingkai dengan Hakim 1 (dicatat, putusan tidak berubah):** kartu `H-P-10-00.md` menulis judul "dilewati bila `null` **atau perangkat legacy**" dan mencantumkan kasus legacy sebagai bagian bukti. Menurut pembacaan saya, kasus legacy (perangkat tanpa baris `kredensial_perangkat`) adalah perilaku **demi desain** dan sudah dibantah eksplisit oleh baris temuan sendiri ("bantahan perangkat legacy tanpa key dipatahkan asersi hash memang ada") — lingkup temuan adalah null-skip pada perangkat **ber-key**. Karena putusan akhir (TERVERIFIKASI K-1) sama, perbedaan ini hanya dicatat sesuai aturan sengketa README.
- **Tingkat K:** **K-1 dipertahankan** (kategori "akses tanpa hak": faktor autentikasi kedua — rahasia perangkat — terlewati total; sejalan dua hakim F-03 yang independen dan Hakim 1). Berbeda dari PMB1-F-036 (owner mendaftarkan perangkat baru) dan PMB1-F-039 (orakel UUID asing): akar masalah berbeda (0087:267) dengan prasyarat berbeda (perangkat terdaftar yang ber-key).
- **Putusan:** **TERVERIFIKASI**.

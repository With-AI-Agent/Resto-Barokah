### 3.6 Role-switching: apakah pembeda berbasis role bisa dipalsukan? (keluaran mentah)

Pertanyaan turunan penting untuk desain perbaikan: apakah sesi `authenticated` bisa "menyamar" menjadi `service_role`? Uji dijalankan di db `postgres` (cluster KERJA).

Uji 1 — urutan SET ROLE dari sesi yang login sebagai `postgres` (superuser — persis arsitektur Supabase, di mana koneksi datang sebagai role `postgres`):

```text
--- A: langsung dari postgres (superuser) ---
  OK   'begin' -> ('postgres', 'postgres')
  OK   'set local role authenticated' -> ('authenticated', 'postgres')
  OK   'set local role service_role' -> ('service_role', 'postgres')
  OK   'commit' -> ('postgres', 'postgres')
--- B: dari authenticated (SET ROLE berturut) ---
  OK   'begin' -> ('postgres', 'postgres')
  OK   'set local role authenticated' -> ('authenticated', 'postgres')
  OK   'set local role service_role' -> ('service_role', 'postgres')
  OK   'commit' -> ('postgres', 'postgres')
```

Uji 2 — login BUKAN superuser dan bukan anggota apa pun (role sementara `t05login`, dibuat-hapus selama uji):

```text
--- LOGIN t05login (bukan superuser, bukan anggota apa pun) ---
  OK   'select current_user, session_user' -> ('t05login', 't05login')
  DITOLAK [42501] 'set local role authenticated' -> permission denied to set role "authenticated"
  DITOLAK [42501] 'set local role service_role' -> permission denied to set role "service_role"
```

Uji 3 — keanggotaan & ke-settable-an GUC `role` (dari sesi S3, `authenticated` tanpa sub):

```text
  select pg_has_role('authenticated','service_role','member') -> (False,)
  select pg_has_role('postgres','service_role','member')      -> (True,)
  S3 GUC role sekarang                                      -> ('authenticated',)
  S3 coba SET ROLE service_role                             -> OK (lihat Uji 1: hanya karena session user = superuser)
  S3 coba set_config('role','service_role',true)            -> ('service_role',)   # GUC 'role' BISA di-SET klien!
```

Arti (bukti, bukan asumsi):
1. Aturan resmi PostgreSQL untuk `SET ROLE`: hak dicek terhadap **session user** (bukan current role) — "The current session user must have the SET option for the specified role_name … (**If the session user is a superuser, any role can be selected.**)" (dok resmi, §3.8). Karena Supabase menyambungkan SEMUA sesi (termasuk klien via PostgREST) sebagai `postgres` (superuser), role SQL TIDAK bisa menjadi batas kepercayaan dalam model deployment ini — tetapi jalur ini butuh akses SQL langsung (kredensial DB) atau kode peladen, BUKAN peramban (PostgREST tidak menjalankan SQL mentah).
2. GUC `role` (mencerminkan `SET ROLE`; tidak di-reset di dalam definer — terukur FASE 2) **bisa di-`set_config` dari sesi klien** → juga bukan pembeda tepercaya.
3. Satu-satunya penanda yang diisi dari **JWT terverifikasi** (PostgREST menyuntikkan klaim; library server Supabase "meng-injeksi klaim pemanggil dan menurunkan role" per dok resmi) adalah GUC `request.jwt.claims` — itulah dasar kandidat MUTASI B. Sesi SQL mentah memang bisa juga meng-`set_config` klaim, tetapi sesi yang sudah memegang kredensial DB berada di atas model ancaman yang disepakati (bisa membaca tabel langsung sebagai pemilik); nilai perbaikan adalah menegakkan kontrak kode di level DB dan menutup bug kode peladen.

## 4. Analisis dan rekomendasi

### 4.1 Akar penyebab yang DIBUKTIKAN

1. **Asumsi "tanpa identitas = jalur peladen"** (`0010:188-190`) memakai *absennya klaim `sub`* sebagai penanda kepercayaan. Di PostgreSQL, role (`authenticated`) dan klaim `sub` orthogonal: sesi bisa `authenticated` TANPA `sub` (SQL langsung, atau kode peladen yang salah konfigurasi). Akibatnya di dua RPC definer:
   - `total_dibayar` (0010:200): `auth.uid() is null or …` → cabang null **melewatkan filter penyewa** → total uang penyewa lain terbaca (62100 vs 0 untuk kasir B ber-identitas — fixture yang sama, non-kosong).
   - `hitung_total` (0015, efektif): guard `if auth.uid() is not null and not pesanan_sepenyewa(…)` → **identitas null melewati guard** → fungsi definer menulis ulang kolom uang pesanan penyewa lain (bukti 0 → 62100 tersimpan; RLS dilewati karena definer).
2. **Pembeda berbasis role buta di dalam definer** — terukur (FASE 2/6): `current_user` di dalam definer = `postgres` (pemilik fungsi) untuk SEMUA pemanggil, termasuk klien `authenticated`; `session_user` = role koneksi (di Supabase: `postgres` untuk semua sesi, klien maupun server) → juga tak membedakan; `peran_peladen()` = `true` selalu di dalam definer; GUC `role` = bisa di-`set_config` dari sesi klien. Komentar kode sendiri (0010:155-160) sudah mengakui buta-nya `current_user`/`peran_peladen()` — dan karena itu `total_dibayar` TIDAK memakai `peran_peladen()` (0010:186-189), tetapi penganti yang dipilih (absen `sub`) justru punya lubang yang sama untuk sesi `authenticated`-tanpa-`sub`.
3. **Permukaan bocor terbatas pada RPC definer yang bisa dipanggil klien** — RLS tabel tetap menahan DML langsung (0 baris / 42501), dan 14 titik pemicu `auth.uid() is null or …` terlindungi RLS tabelnya (katalog: kombinasi definer/non-definer tercantum FASE 5; tidak ada satu pun pemicu yang bisa dipanggil langsung sebagai RPC efektif — 0023 mencabut EXECUTE 20 pemicu definer; 11 pemicu non-definer masih EXECUTE terbuka tetapi pemanggilan langsung tanpa efek NEW/OLD, sesuai catatan AUD-2 F-06, di luar cakupan T-05).

### 4.2 Tiga kesimpulan dipisah (tidak dicampuradukkan)

1. **Perilaku SQL — TERVERIFIKASI:** pada target utuh (PostgreSQL 16.2 asli, 2 database independen; plus kontrol PGlite 65/65), sesi `authenticated` tanpa `sub` (a) membaca total pembayaran penyewa lain lewat `total_dibayar` dan (b) menulis kolom uang penyewa lain lewat `hitung_total` — sedangkan kontrol ber-identitas-sah ditolak/0. Kontrol "nol dari fixture kosong" dijaga: `total_dibayar(pesananA)` = 0 untuk S2 berasal dari guard (data ada — 1 baris 62100 terverifikasi pemilik), bukan karena tabel kosong; dan S3 pada pesanan TIDAK berbayar memang 0 (dinyatakan bukan bukti isolasi).
2. **Pelanggaran kontrak — TERVERIFIKASI di level DB:** PRD Aturan Bisnis 9, KEAMANAN §2 ("Janji utama platform"), dan komentar kode 0010:180-189 sendiri ("tanpa pemeriksaan di sini siapa pun yang masuk bisa membaca angka uang pesanan resto LAIN hanya dengan menebak UUID") dilanggar oleh perilaku di atas. Klaim 0022:6-7 "Tidak ada bypass auth.uid() null" tidak berlaku untuk permukaan RPC definer (hanya untuk jalur yang diuji 0022).
3. **Keterjangkauan klien — BELUM TERVERIFIKASI (DUGAAN):** peramban/PostgREST mengisi klaim dari JWT terverifikasi (dok §3.8 no.3/4); tidak ada jalur peramban yang bisa mengeksekusi SQL mentah; jalur nyata (koneksi DB langsung / kode peladen tanpa klaim) butuh kredensial atau bug peladen. **Tidak ada klaim eksploitasi jarak jauh terbukti** — sama persis dengan "batas jujur" auditor AUD-2, dan bantah-balik saya tidak mengubah status itu.

### 4.3 Bantah-balik usulan auditor (tugas paket §3.6)

- **`auth.uid() is null and current_user <> 'authenticated'` — TERBANTAH:** di dalam definer `current_user` = `postgres` (terukur FASE 2 untuk semua profil) → ekspresi bernilai `true` untuk sesi `authenticated` tanpa sub → **MUTASI A: lubang tetap bocor (62100)**. Usulan itu hanya efektif di konteks NON-definer (pemicu), sedangkan permukaan bocornya justru RPC definer.
- **`peran_peladen()` — TERBANTAH sebagai penjaga definer:** selalu `true` di dalam definer (terukur: `DARI-DALAM-DEFINER: peran_peladen()=true, current_user=postgres`); kata-kata auditor "di luar fungsi definer" tidak bisa diterapkan pada badan `total_dibayar` yang definer (dan helper non-definer yang dipanggil dari definer tetap mengevaluasi `current_user`=pemilik — terukur).
- **Yang LAYAK (dibuktikan bekerja):** pembeda berbasis **klaim terverifikasi** — MUTASI B (`role = 'service_role'` di `request.jwt.claims`, dengan `is true` anti-logika-tiga-nilai) menutup kedua fungsi untuk S3, mempertahankan S1/S2 dan jalur peladen ber-klaim, serta tidak mematikan jalur pemicu sah (void `sebelum_dapur` → hitung ulang via trigger → keadaan akhir `('batal', 0, 0)`). Konsekuensi jujur yang DIBUKTIKAN juga: `service_role` TANPA klaim terblok (MUT-B S5 = 0) → inventaris jalur peladen yang menyetel klaim WAJIB sebelum perbaikan diterapkan.

### 4.4 Peta jalur sah yang memang butuh identitas kosong (JANGAN ditolak semua null secara buta)

### 4.5 Severity yang dapat dipertanggungjawabkan

**K-2 dipertahankan** (tidak dinaikkan, tidak diturunkan):
- Tidak K-1: tidak ada jalur eksploit jarak jauh yang terbukti (keterjangkauan klien tetap DUGAAN; PostgREST + JWT terverifikasi).
- Tidak diturunkan: perilaku SQL direproduksi di 2 engine (PGlite suite + PG 16.2 asli) × 2 database, dengan kontras kontrol yang ditolak; melanggar kontrak PRD/KEAMANAN/komentar-kode sendiri; permukaan = RPC definer yang memang dirancang sebagai "penjaga isolasi" (AUD-3 K-1 dulu) dan bisa dipanggil oleh pemegang kredensial DB / kode peladen buggy.
- Temuan tambahan saya (F-T05-1 GUC `role` ke-settable; F-T05-2 role-switch superuser di model Supabase) **tidak menaikkan** severity A-F02 karena keduanya berada di atas model ancaman yang disepakati (akses SQL langsung) — dicatat untuk ledger, bukan untuk eskalasi.

### 4.6 Rekomendasi desain/tes untuk integrator (TANPA migrasi/perubahan kode dari pekerja ini)

1. **R1 — pembeda berbasis klaim di RPC definer** (mengganti asumsi "null = peladen"): `total_dibayar` dan `hitung_total` (efektif 0015) memakai "identitas null dianggap peladen HANYA jika `request.jwt.claims` ber-`role = 'service_role'`" (pola MUTASI B, termasuk `is true`). Inventaris dulu SEMUA jalur peladen (Edge Function `supabase/functions/*` + kode server lain) untuk memastikan mereka menyetel klaim sesuai pola dokumentasi Supabase; putuskan eksplisit nasib `service_role`-tanpa-klaim (MUT-B membuktikannya terblok — konsekuensi, bukan bug).
2. **R2 — uji tetap** (usul nama `supabase/tes/isolasi_null_identitas.sql`): sebagai `set local role authenticated` + GUC sub kosong: (a) `total_dibayar(<pesanan penyewa lain>) = 0`, (b) `hitung_total(<pesanan penyewa lain>)` ditolak `Pesanan itu bukan milik resto Anda.`, (c) kontrol S1/S2 tak berubah, (d) kontrol jalur peladen ber-klaim tetap 62100; perintah hijau `node alat/uji-sql.mjs supabase/tes/isolasi_null_identitas.sql`; tambah mutasi "cabang null-identitas dibuka" di harness mutasi (wajib MERAH-PAGAR, klasifikasi `klasifikasi_mutasi.py`).
3. **R3 — larangan pembeda buta:** jangan memakai `current_user` (di definer = pemilik fungsi), `peran_peladen()` (di definer = selalu true), `session_user` (= role koneksi), atau GUC `role` (ke-settable) — keempatnya dibuktikan/diukur tidak efektif (§3.6, MUTASI A).
4. **R4 — seragamkan 14 titik** `auth.uid() is null or …` ke satu helper penyediaan akses (tulis pembeda SATU kali) + peta titik (trigger = terlindungi RLS, prioritas rendah; RPC definer = prioritas 1). Nomor migrasi baru dipilih integrator, bukan pekerja.
5. **R5 — catat ke ledger** (TINDAK_LANJUT/AUDIT_RIWAYAT): F-T05-1 (GUC `role` ke-settable; PG 16.2) dan F-T05-2 (di model Supabase, session user superuser → `SET ROLE` bebas; login non-superuser tetap 42501) — di atas model ancaman, tanpa aksi sekarang.

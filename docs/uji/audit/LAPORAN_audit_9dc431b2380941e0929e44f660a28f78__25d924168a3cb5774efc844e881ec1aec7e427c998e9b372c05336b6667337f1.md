## 4. Temuan

### [F-01] Login staf berhasil TANPA perangkat terdaftar (faktor perangkat bisa dihilangkan)
- **Tingkat:** K-2
- **Artefak:** `supabase/migrations/0061_verifikasi_pin_perangkat.sql:62-95`
- **Klaim yang dilanggar:** `docs/KEAMANAN.md` §1.3 ("Dua faktor untuk semua orang yang menyentuh uang. Staf: perangkat terdaftar (yang dimiliki) + PIN (yang diketahui)") dan §5 ("Tanpa perangkat terdaftar, PIN tidak menghasilkan sesi yang bisa dipakai").
- **Bukti:** `node alat/uji-sql.mjs /tmp/audit/serangan/s03c_pin_sesi.sql` → `C1 login tanpa perangkat => BOCOR(LOGIN_SUKSES)`. Kode: `if p_perangkat_id is not null then … else v_alat_nama := coalesce(p_perangkat_nama, 'tidak-diketahui'); end if;` — seluruh validasi perangkat dilewati bila parameter dikosongkan; fungsi di-grant `to anon`.
- **Skenario gagal:** Penyerang yang mengetahui email + PIN 6 digit seorang kasir (PIN dibagikan/diintip — risiko sisa §15.3 diakui proyek) memanggil RPC `verifikasi_pin_perangkat` tanpa `p_perangkat_id` → login sukses dari perangkat mana pun di internet, tanpa pernah punya perangkat terdaftar; lapis dua-faktor runtuh jadi satu faktor.
- **Dugaan penyebab:** Parameter `p_perangkat_id` dibuat opsional (default null) untuk mengakomodasi klien lama, tetapi tidak ada jalur fallback yang menolak saat perangkat absen.
- **Cara membuktikan perbaikan:** uji SQL baru: `select uji.harap_gagal_sebab($$select public.verifikasi_pin_perangkat('kasir@x','246810',null,null)$$, 'perangkat', …)` harus merah bila LOGIN_SUKSES; setelah perbaikan, uji itu hijau dan `s03c` C1 berubah AMAN.
- **Status verifikasi:** TERVERIFIKASI

### [F-02] Kunci rahasia perangkat (`kunci_hash`) tidak diverifikasi pada login staf 0061
- **Tingkat:** K-2
- **Artefak:** `supabase/migrations/0061_verifikasi_pin_perangkat.sql:62-72` vs `supabase/migrations/0018_perangkat_terdaftar.sql:88-100`
- **Klaim yang dilanggar:** `docs/KEAMANAN.md` §4 ("server hanya menyimpan SHA-256" dari rahasia perangkat — rahasia itu faktor kepemilikan) dan pola `perangkat_sah(id, kunci)` yang dipakai `verifikasi_pin` (0018).
- **Bukti:** Baca kode: langkah 3 fungsi 0061 hanya `select … from public.perangkat where id = p_perangkat_id` (ada/aktif/penyewa/peran) — TIDAK ADA join `kredensial_perangkat`/`crypt(kunci)`; fungsi bahkan tidak menerima parameter kunci. Bandingkan `perangkat_sah()` di 0018 yang memverifikasi hash kunci. Uji C2 (`s03c`) membuktikan pengecekan hanya keberadaan baris.
- **Skenario gagal:** UUID `perangkat` (diproduksi dari `crypto.randomUUID()` di localStorage, dikirim sebagai parameter terbuka, bisa dibaca XSS/log proxy) sudah cukup meniru "perangkat terdaftar" — tanpa rahasia 32-byte yang dijanjikan dokumen.
- **Dugaan penyebab:** RPC login baru (N F-01) menulis ulang alur perangkat tanpa memakai `perangkat_sah()` yang sudah ada.
- **Cara membuktikan perbaikan:** `verifikasi_pin_perangkat` menerima `p_perangkat_kunci` dan memanggil `perangkat_sah()`; uji SQL: kunci salah atas perangkat sah → ditolak.
- **Status verifikasi:** TERVERIFIKASI

### [F-03] Alur masuk aplikasi tidak mungkin sukses terhadap database nyata (UUID lokal tak pernah terdaftar; RPC pengikat sesi tak punya pemanggil)
- **Tingkat:** K-2
- **Artefak:** `aplikasi/src/lib/auth.ts:39-57,137,176-181` + `supabase/migrations/0061_verifikasi_pin_perangkat.sql:62-70`
- **Klaim yang dilanggar:** DoD T2-01/T2-02 (layar masuk pegawai bekerja) dan janji KEAMANAN §5 bahwa perangkat terdaftar + PIN "menghasilkan sesi yang bisa dipakai".
- **Bukti:** (a) `ambilPerangkatLokal()` membuat UUID acak di localStorage; `masukDenganPin` mengirimkannya sebagai `p_perangkat_id`. Serangan C2 membuktikan UUID tak terdaftar → `PERANGKAT_TIDAK_SAH`, jadi login nyata SELALU gagal. (b) `grep -rn "buat_kode_perangkat\|daftarkan_perangkat_dengan_kode\|ikat_sesi_perangkat\|akhiri_sesi\|cabut_perangkat" aplikasi/src` (di luar uji) → 0 pemanggil: tidak ada UI pendaftaran perangkat, pengikatan sesi, atau pencabutan di aplikasi. (c) Konsekuensi lanjutan: karena login PIN tidak membuat sesi Supabase Auth apa pun, hook data (`hook/useBayar.ts:125,172`, `hook/useStok.ts:135`, `App.tsx:63-164`) berjalan dengan klien anonim → RLS menolak (dibuktikan A1: anon melihat 0 baris). Uji komponen lulus karena RPC di-mock (harness), bukan bukti alur nyata (L4: lulus karena sebab yang salah).
- **Skenario gagal:** Pemilik menyebar aplikasi (workflow `sebar-halaman.yml` siap), kasir mencoba masuk di tablet → selalu "Perangkat tidak terdaftar atau telah dicabut."; satu-satunya cara membuat login "berhasil" adalah jalur tanpa perangkat (F-01) — yakni jalur yang lebih lemah.
- **Dugaan penyebab:** Integrasi app↔Auth tertinggal dari lapisan database: RPC 0061 dibuat menutup temuan N F-01 tanpa menyambung alur pendaftaran/pengikatan perangkat di sisi aplikasi.
- **Cara membuktikan perbaikan:** uji integrasi (mis. vitest dengan klien PGlive/PGlite atau e2e Playwright T11-11): daftar perangkat via kode → login PIN sukses → `bayar_pesanan` tercatat dengan identitas. Perintah hijau: `cd aplikasi && npm test` + e2e baru + serangan C2 berubah jadi "login perangkat sah = LOGIN_SUKSES".
- **Status verifikasi:** TERVERIFIKASI

### [F-04] Penegakan sesi/perangkat di database bersifat opt-in per klaim; token tanpa klaim `session_id` melewati pencabutan
- **Tingkat:** K-2
- **Artefak:** `supabase/migrations/0058_sesi_masih_aktif.sql:46-97`
- **Klaim yang dilanggar:** `docs/KEAMANAN.md` §1.4 ("Pencabutan tidak menunggu token kedaluwarsa … semua pemeriksaan perangkat/sesi dilakukan di database pada setiap permintaan") dan §4 ("Pencabutan seketika … ditolak di database pada detik berikutnya").
- **Bukti:** Serangan C6a–C6c (`/tmp/audit/serangan/s03c_pin_sesi.sql`): sesi aktif dikenali → AMAN; sesi dicabut dengan klaim → gugur → AMAN; tetapi `C6c token TANPA klaim session_id setelah pencabutan => BYPASS(identitas penuh)`. Kode: semua pemeriksaan dibungkus `if v_session_id is not null then …` / `if v_perangkat_id is not null then …` — bila token tidak membawa klaim itu, fungsi langsung `return true`. Referensi perilaku sistem luar: setiap access token Supabase memuat klaim `session_id` (https://supabase.com/docs/guides/auth/sessions, https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook) — artinya token resmi Supabase justru MEMERLUKAN baris `sesi_perangkat` yang cocok; karena aplikasi tidak pernah memanggil `ikat_sesi_perangkat` (F-03), pengguna jalur Supabase Auth terkunci keluar, sedangkan jalur apa pun yang tokennya tanpa klaim lolos tanpa pemeriksaan. Janji "diperiksa pada setiap permintaan" tidak terpasang pada salah satu dari dua keadaan nyata.
- **Skenario gagal:** Perangkat/sesi staf dicabut admin ("Cabut perangkat"); bila akses apa pun memakai token tanpa klaim sesi (mis. klien non-standar, token yang diperbarui tanpa pengikatan, atau jalur masa depan yang menerbitkan token sendiri), akses terus hidup sampai token kedaluwarsa — mantan pegawai tetap bisa masuk.
- **Dugaan penyebab:** Penegakan dibaca dari klaim JWT yang keberadaannya tidak diwajibkan; tidak ada jalur default "tanpa klaim = wajib ditolak" (deny-by-default, prinsip §1.1).
- **Cara membuktikan perbaikan:** `sesi_masih_aktif()` menolak bila `session_id` absen untuk peran non-service (atau mewajibkan pengikatan tercatat); uji: ulang C6c harus gugur; `supabase/tes/sesi_dan_perangkat.sql` tetap hijau.
- **Status verifikasi:** TERVERIFIKASI

### [F-05] `verifikasi_rantai_audit(p_penyewa_id)` membuka metadata audit lintas penyewa
- **Tingkat:** K-3
- **Artefak:** `supabase/migrations/0029_audit_kekal_rantai.sql:118-183`
- **Klaim yang dilanggar:** Janji isolasi penyewa `docs/KEAMANAN.md` §2 ("Isolasi antar penyewa — janji utama platform").
- **Bukti:** Serangan A7 (`/tmp/audit/serangan/s01_tail2.sql`): sebagai kasir tenant A, `select * from public.verifikasi_rantai_audit('22222222-2222-2222-2222-222222222222')` → `A7 … => BOCOR(status/jumlah tenant B terbaca)`. - **Cara membuktikan perbaikan:** tambahkan `if auth.uid() is not null and v_target_penyewa is distinct from public.penyewa_saya() then return … 'tidak ditemukan' end if;`; uji A7 menjadi AMAN.

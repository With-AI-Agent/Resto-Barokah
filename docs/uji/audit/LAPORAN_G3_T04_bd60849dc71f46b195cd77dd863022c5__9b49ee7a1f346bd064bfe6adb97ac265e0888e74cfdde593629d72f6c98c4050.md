
### 3.5 Mekanisme — pesanan utama vs sub-pernyataan CTE (diukur, bukan dikutip)

Pemicu probe **ditambahkan di database uji saja** (bukan berkas repo) untuk mencatat apa yang dilihat pemicu dan `cmin` baris jejaknya (`probe_f01c.py`, 3 ulangan, log dikosongkan tiap serangan):

```
== Serangan satu-pernyataan (CTE bayar + UPDATE catatan), pesanan BARU tiap ulangan ==
  ulangan 1: DITERIMA
      jejak #1: pesanan.UPDATE      baris_pembayaran_dilihat_pemicu=0  cmin=1
      jejak #2: pembayaran.INSERT   baris_pembayaran_dilihat_pemicu=0  cmin=3
      sesudah commit: bayar=(1, 1) catatan='diubah'
  ulangan 2: DITERIMA   … #1 cmin=1 (lihat=0), #2 cmin=3 (lihat=0) …
  ulangan 3: DITERIMA   … #1 cmin=1 (lihat=0), #2 cmin=3 (lihat=0) …
== Serangan dua pernyataan (pernyataan ke-2) sebagai pembanding ==
  pernyataan kedua: DITOLAK [P0001] BY-201 …   jejak pemicu pada pernyataan kedua: []
```

`probe_f01b.py` mengulang kedua urutan **lima kali**: urutan "CTE bayar → utama perubahan" **DITERIMA 5/5**; urutan terbalik "CTE perubahan → utama INSERT bayar" **DITOLAK BY-201 5/5`. Jadi pada build ini urutannya tampak stabil, tetapi saya **tidak** menyebutnya deterministik sebagai jaminan: dokumen resmi menyatakan urutannya *unpredictable* (§3.8), dan yang menjelaskan hasil ini adalah **snapshot yang sama** — penjaga tidak dapat "melihat" sub-pernyataan CTE, apa pun urutannya.

`probe_f01f.py` — atribusi lapis penjaga (tiap himpunan dijalankan di **database uji baru**, pemicu 0022 dilepas di DB uji saja):

```
===== tanpa pelepasan =====
  catatan header (nonnominal) : DITERIMA   (uang tersimpan=1)      <- celah
  qty item (nominal)          : DITOLAK BY-201                     <- oleh zzz_pesanan
  catatan item (nonnominal)   : DITERIMA   (uang tersimpan=1)      <- celah
  diskon / void resmi / item baru : DITOLAK BY-201                 <- zzz (via hitung_total) & aaa_item
===== lepas zzz_pesanan =====
  qty item: DITERIMA   diskon: DITERIMA   item baru: DITERIMA
  void resmi: DITOLAK BY-201 (pesan aaa)                           <- ditahan aaa_item
===== lepas aaa_item + zzz_pesanan =====
  void resmi: DITERIMA                                             <- aaa_pembatalan SENDIRI tidak menahan
===== lepas aaa_item + aaa_pembatalan =====
  void resmi: DITOLAK BY-201 (pesan zzz)                           <- lapis cadangan zzz
===== lepas keempat pemicu 0022 =====  semua DITERIMA
```

Bacaan: **qty/diskon/item-baru ditahan sabuk header (zzz) lewat perhitungan ulang `hitung_total`**, **void ditahan penjaga rincian (aaa_item)**, sedangkan **`aaa_pembatalan` tidak pernah menjadi penahan pada kelas satu-pernyataan** (baris uang di perintah yang sama tidak terlihat). Ini bukan penilaian atas niat penulis migrasi; ini pengukuran lapis mana yang benar-benar bekerja.

### 3.7 Keterjangkauan klien — dipisahkan dari kemampuan SQL

| Fakta terukur | Nilai |
|---|---|
| Hak tabel `authenticated` (dari katalog DB uji) | `INSERT` pada `pembayaran` = **true**; `UPDATE` pada `pesanan` = **true**; `UPDATE` pada `pesanan_item` = **true** |
| RLS | aktif pada `pesanan`, `pesanan_item`, `pembayaran` (`relrowsecurity = true`) |
| RPC yang mencatat pembayaran | **tidak ada**: `git grep -in "insert into public.pembayaran" <SHA target> -- supabase` hanya menemukan berkas **tes**, tidak ada migrasi/fungsi/Edge Function. Jadi pembayaran memang dicatat klien lewat tabel langsung (PostgREST), bukan lewat RPC |
| Kode aplikasi | `aplikasi/package.json` memakai `@supabase/supabase-js` 2.116; belum ada layar/alur bayar (`aplikasi/src/layar/README.md`: kasir = Fase 3); tidak ada kode yang menulis `pembayaran` |
| Bentuk pernyataan yang dibutuhkan serangan | **satu** pernyataan SQL berisi CTE data-modifying lintas tabel (`pembayaran` + `pesanan`/`pesanan_item`) |

**Kesimpulan:** kemampuan SQL **terbukti** (siapa pun yang bisa mengirim pernyataan itu sebagai `authenticated`), tetapi **keterjangkauan dari klien aplikasi BELUM TERBUKTI** — tidak ada RPC yang menyediakan bentuk itu, dan klien PostgREST/supabase-js mengirim satu operasi tabel per permintaan (dua permintaan = dua transaksi = bentuk dua-pernyataan yang sudah ditolak). Saya **tidak** membuktikan ketidakmungkinan menyeluruh (mis. fitur tulis-bertingkat PostgREST, atau klien dengan kredensial DB langsung) — karena itu saya tidak menaikkan tarafnya.

### 3.8 Dokumentasi resmi yang dipakai (bukan sebagai pengganti hasil eksekusi)

- PostgreSQL 16, §7.8.4 *Data-Modifying Statements in `WITH`* — <https://www.postgresql.org/docs/16/queries-with.html> (diakses **2026-09-21**), kutipan: *"The sub-statements in `WITH` are executed concurrently with each other and with the main query. Therefore, when using data-modifying statements in `WITH`, the order in which the specified updates actually happen is unpredictable. All the statements are executed with the same snapshot …, so they cannot 'see' one another's effects on the target tables."* → ini akar penyebab yang terukur di §3.5 (penjaga berbasis `exists(pembayaran)` tidak melihat baris uang dari sub-pernyataan CTE yang sama).
- Dokumen yang sama juga memperingatkan agar menghindari sub-pernyataan `WITH` yang menyentuh baris yang sama dengan pernyataan utama (*"The effects of such a statement will not be predictable"*) — relevan bagi desainer perbaikan kelak.
- Aturan produk yang diklaim dilanggar (dibaca di target): `docs/PRD.md` M6 baris 136 (*"Sesudah pembayaran pertama, termasuk sebagian: isi/nominal, diskon, dan void dikunci (T-025(a))"*), `docs/PRD.md` Aturan Bisnis 7 baris 267, `docs/TECH_SPEC.md` baris 95 (§2 butir 6), `docs/ROADMAP.md` baris 625 (T-025(a) → penegak 0022). Tidak ada keputusan uang baru yang saya buat: saya hanya menguji teks yang sudah dikunci.

## 4. Analisis dan rekomendasi

### 4.1 Akar penyebab yang dibuktikan

Pagar beku 0022 menguji **"apakah ada baris uang yang terlihat"** (`exists (select 1 from public.pembayaran …)`). Dalam satu pernyataan dengan CTE data-modifying, semua bagian pernyataan memakai **snapshot yang sama** dan **tidak dapat melihat efek satu sama lain** (dokumen resmi, §3.8) — terukur: pemicu pada `pesanan`/`pesanan_item` melihat **0** baris pembayaran (`cmin` pernyataan utama 1, `INSERT` pembayaran dari sub-pernyataan CTE `cmin` 3, jejak log pemicu probe §3.5). Karena itu, untuk pesanan yang **belum** punya uang, perubahan jejak nonnominal lolos bersamaan dengan pencatatan pembayaran pertama.

Yang **tidak** terjadi (penting agar perbaikan tidak salah sasaran):
- sekali ada satu baris uang, bentuk satu-pernyataan **tetap ditolak** (§3.4 D2/D6) — jadi pagar itu tidak "hilang", ia hanya tidak melihat uang yang lahir di perintah yang sama;
- bidang **nominal** (qty, diskon, item baru, `total`, status batal) **tetap tertahan** di bentuk satu-pernyataan, dan §3.5 menunjukkan penahannya adalah `zzz_pesanan` lewat perhitungan ulang `hitung_total`, sedangkan void ditahan `aaa_item`;
- `aaa_pembatalan` **tidak** pernah menjadi penahan pada kelas ini (temuan atribusi).

### 4.2 Alternatif/tuduhan yang saya coba bantah sendiri (dan hasilnya)

1. **"Uang yang sudah ada bisa dilewati dengan menyisipkan bayar ke-2 di CTE."** → **TERBANTAH**: D2/D6 ditolak BY-201, tidak ada perubahan maupun baris uang ke-2.
2. **"Nominal juga bisa dilewati."** → **TERBANTAH**: qty/diskon/item baru/`total` semuanya ditolak (§3.3, §3.5).
3. **"Yang bocor adalah kemampuan baru."** → **TERBANTAH**: keenam bidang itu sah diubah sebelum uang ada (§3.7 L), dan keadaan akhir serangan bisa dicapai jalur sah (D4).
4. **"PGlite tidak kesetiaan dengan PG nyata (sehingga suite 65/65 buta karena mesinnya)."** → **TERBANTAH oleh pengukuran saya sendiri**: probe PGlite pertama saya kebetulan menaruh pembayaran lebih dulu sehingga ditolak (bukti D2, bukan beda mesin). Setelah kanal dan urutan dipisah dengan benar, **PGlite 0.3.16 dan PG 16.2 sama-sama menerima** serangan inti (§3.2). Buta-tidaknya suite disebabkan **cakupan uji**, bukan mesin.
5. **"Keterjangkauan klien mudah."** → **TIDAK TERBUKTI**: tidak ada RPC pencatat pembayaran; klien aplikasi belum punya alur bayar; PostgREST/supabase-js mengirim satu operasi tabel per permintaan. Saya tidak memakai ini untuk membatalkan perilaku SQL-nya, tetapi juga tidak menaikkan dampaknya menjadi klaim "browser bisa".

### 4.3 Dampak yang benar-benar terbukti (batas klaim)

- Yang **terbukti**: pada pesanan **belum** berbayar, satu pernyataan SQL sebagai `authenticated` (kasir cabang itu) dapat mencatat pembayaran pertama **dan** mengubah jejak (`catatan`, `tipe`, `meja_id`, `pelayan_id`, `shift_id`, `pesanan_item.catatan`) dalam satu perintah, dengan **uang tersimpan** (§3.2) dan tanpa BY-201.

````python
"""EKSPERIMEN T-04 — kalibrasi mutan untuk USULAN regresi beku_satu_pernyataan.sql.

Meniru pola alat/uji-mutasi-0022.py: salinan sementara, berkas 0022 dimutasi di

from __future__ import annotations

import importlib.util
import pathlib
import shutil
import subprocess
import tempfile

SALINAN = pathlib.Path('/tmp/g3t04-QfBMxO/target')
USULAN = pathlib.Path('/tmp/g3t04-QfBMxO/probe/beku_satu_pernyataan.sql')

spec.loader.exec_module(kl)

UJI = 'supabase/tes/beku_satu_pernyataan.sql'

    ('M1 sabuk header (zzz) dilepas', asli + '\ndrop trigger zzz_pesanan_beku_setelah_bayar on public.pesanan;', kl.MERAH_PAGAR),
    ('M2 penjaga item (aaa_item) dilepas', asli + '\ndrop trigger aaa_item_beku_setelah_bayar on public.pesanan_item;', kl.MERAH_PAGAR),
    ('M3 aaa_item + zzz dilepas (void lolos)', asli + '\ndrop trigger aaa_item_beku_setelah_bayar on public.pesanan_item;'
     '\ndrop trigger zzz_pesanan_beku_setelah_bayar on public.pesanan;', kl.MERAH_PAGAR),
    ('M4 semua penjaga 0022 dilepas', asli + '\ndrop trigger aaa_item_beku_setelah_bayar on public.pesanan_item;'
     '\ndrop trigger aaa_diskon_beku_setelah_bayar on public.diskon_transaksi;'
     '\ndrop trigger aaa_pembatalan_beku_setelah_bayar on public.pembatalan;'
     '\ndrop trigger zzz_pesanan_beku_setelah_bayar on public.pesanan;', kl.MERAH_PAGAR),
    # Temuan atribusi: aaa_pembatalan TIDAK menopang pagar void di kelas satu-pernyataan
    # (baris uang di perintah yang sama tak terlihat) — dilepasnya tidak membuat usulan
    # regresi merah; M3/M4 yang membuktikan pagar itu memang dipegang lapis lain.
    ('M5 aaa_pembatalan dilepas saja (tetap HIJAU — temuan atribusi)', asli + '\ndrop trigger aaa_pembatalan_beku_setelah_bayar on public.pembatalan;', kl.HIJAU),

        r = subprocess.run(['node', 'alat/uji-sql.mjs', UJI], cwd=root, capture_output=True, text=True, timeout=180)

        ok = jenis == harap
        gagal += not ok
        print(f"{'OK' if ok else 'GAGAL'} {nama}: {jenis} {sebab[:150]}")
    print(f'HASIL: {"LOLOS" if not gagal else "GAGAL"} — usulan regresi peka terhadap pelepasan pagar; {gagal} tidak sesuai.')
````
